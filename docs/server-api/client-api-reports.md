# Client API — Reports & Processors (генераторы .erf / .epf)

> Часть client-контракта. Индекс: [client-api.md](client-api.md).

## POST /v1/api/reports/generate-erf

Генерирует внешний отчёт 1С (СКД, `.erf`) из текста запроса и возвращает готовый
бинарь в теле ответа (F-000034, REQ-054). Канонический шаблон отчёта — у сервера;
клиент передаёт только метаданные, текст запроса и упорядоченный список полей.

Auth: `Authorization: Bearer swan_uk_*` (или InfraConnect per-user ключ) +
`X-Product-Key: swan_pk_*` — как у `/v1/api/updates/download`.
Rate-limit: **30 запросов / 5 минут** на пользователя (`RATE_LIMIT_EXCEEDED` 429).

**Request:**
```json
{
  "queryText": "string, required — текст 1С-запроса; ≤ 4 МБ",
  "fields": ["string, required — поля результата по порядку; 1..500, без дублей и пустых"],
  "reportName": "string, required — человекочитаемое имя отчёта (синоним, презентация варианта, ИмяЭтогоОтчета())",
  "objectName": "string, required — техническое имя объекта отчёта: идентификатор 1С (буквы/цифры/подчёркивания, не с цифры)",
  "parameters": [
    {
      "name": "string, required — имя &параметра запроса (матч с запросом без учёта регистра)",
      "type": ["string, required — нормализованные типы 1С; несколько элементов = составной тип"],
      "isList": "bool — параметр принимает список значений (оператор В (&Параметр))"
    }
  ],
  "resources": [
    {
      "field": "string, required — поле из fields[], выносится ресурсом СКД",
      "function": "string, required — enum: Сумма | Количество | КоличествоРазличных | Среднее | Максимум | Минимум"
    }
  ],
  "groups": [
    { "fields": ["string, required — ≥1 поля уровня группировки, каждое из fields[]"] }
  ],
  "totalsOnly": "bool — true: без детальных записей (только уровни итогов); требует непустой groups",
  "sessionId": "uuid, optional — привязка попытки к диалогу в аудите генераций (T-000336, REQ-062)"
}
```

`parameters` (F-000040, REQ-056, v0.77.0) — опционально, ≤ 100 описаний; **значения
не передаются** — параметры заполняет пользователь в настройках отчёта. Absent/`[]` →
поведение v0.76.0 (поддержана только периодная пара, прочие параметры — отказ).

`resources` / `groups` / `totalsOnly` (T-000301, ANNOUNCE-005) — опциональны и
независимы; absent/`[]`/`false` → прежнее поведение (детальный отчёт без итогов).

`sessionId` (T-000336, REQ-062, v0.84.0) — опционально: id текущего диалога для
привязки попытки в диагностическом аудите. Absent/`""` — генерация разрешена, аудит
без привязки. Непустой обязан принадлежать текущим `user + product` — чужой,
неизвестный или синтаксически невалидный id отклоняется `404 SESSION_NOT_FOUND`
(единый стабильный код, существование чужих диалогов не раскрывается).

Лимит тела запроса — 8 МБ.

**Response (200)** — бинарь, не JSON:

```http
HTTP/1.1 200 OK
Content-Type: application/octet-stream
Content-Disposition: attachment; filename*=utf-8''%D0%9E%D1%82%D1%87%D0%B5%D1%82.erf
Content-Length: <размер>
X-Checksum-Sha256: <hex sha256 тела>
```

Тело читается напрямую (`ПолучитьТелоКакДвоичныеДанные()`), checksum — для сверки
целостности (та же конвенция, что у download обновлений). Частичный ERF невозможен:
тело пишется только после полной сборки и внутренней верификации артефакта
(unpack → pack → re-unpack сравнение содержимого).

### Правила генерации

- `queryText` инъектируется в единственный `DataSetQuery` шаблона как есть,
  с одной нормализацией: концы строк `CRLF`/`CR` приводятся к `LF` (v0.83.1,
  REQ-063) — так текст запроса хранит сам Конфигуратор; на семантику запроса
  это не влияет, слать можно любые концы строк.
- `fields` становятся полями датасета **и** корневыми выбранными полями настроек,
  порядок входа сохраняется. Плюс одна пустая детальная группировка
  (авто-порядок, авто-выбор).
- `reportName` пишется в презентацию варианта настроек, синоним объекта отчёта и
  функцию модуля `ИмяЭтогоОтчета()`; `objectName` — техимя объекта.
- **Периодная пара**: если запрос содержит пару `&НачалоПериода` + `&КонецПериода`
  (без учёта регистра, вне строковых литералов и комментариев) — создаётся один
  параметр отчёта `ПериодОтчета` типа `StandardPeriod`, члены пары биндятся к
  `&ПериодОтчета.ДатаНачала` / `&ПериодОтчета.ДатаОкончания`. Одиночный член пары —
  ошибка `ERF_UNSUPPORTED_PARAMETERS` (имена зарезервированы за периодом, даже если
  описаны в `parameters`). Описания членов пары в `parameters` **разрешены и
  игнорируются** — клиент может слать вывод `get_query_parameters` не фильтруя.
- **Произвольные параметры** (F-000040, REQ-056, v0.77.0): каждый не-периодный
  `&параметр` запроса обязан быть описан в `parameters` — становится параметром
  схемы СКД, доступным в настройках отчёта. Сверка имён с запросом — без учёта
  регистра. Параметр без описания → `ERF_UNSUPPORTED_PARAMETERS`; описание
  отсутствующего в запросе параметра, дубль, пустой/неподдержанный тип →
  `ERF_INVALID_PARAMETERS`. Частичный ERF невозможен — любая ошибка валидации
  отдаётся до сборки.
- **Порядок панели отборов — серверный канон** (порядок входного массива НЕ
  используется): `ПериодОтчета` (+члены пары) всегда первым, затем `Организация`,
  затем `Контрагент`, остальные по алфавиту — конвенция типовых панелей отборов 1С
  (по частоте использования).
- **СКД-совместимость запроса** — сервер валидирует авторитетно (`ERF_INVALID_QUERY`
  400): `АВТОУПОРЯДОЧИВАНИЕ` запрещено (СКД управляет порядком сам); в пакетном
  запросе результатным может быть только **последний** пакет — промежуточные обязаны
  быть `ПОМЕСТИТЬ`/`УНИЧТОЖИТЬ`. Оба правила проверяются вне строковых литералов и
  комментариев. **Рекомендация клиенту:** пред-валидировать те же правила до отправки
  (мгновенная ошибка без round-trip); серверная проверка остаётся источником истины.
- **Поддержанные типы** (нормализованная форма, как в `get_query_parameters`):
  примитивы `Число` (`xs:decimal`), `Строка` (`xs:string`), `Дата` (`xs:dateTime`),
  `Булево` (`xs:boolean`); ссылочные `Справочник.X`, `Документ.X`, `Перечисление.X`,
  `ПланСчетов.X`, `ПланВидовХарактеристик.X`, `ПланВидовРасчета.X`, `ПланОбмена.X`,
  `БизнесПроцесс.X`, `Задача.X` (→ `cfg:*Ref.X`). Несколько элементов `type` —
  составной тип. `isList: true` → `valueListAllowed` (значение-список). Всё прочее
  (`УникальныйИдентификатор`, `ХранилищеЗначения`, таблицы и т.п.) →
  `ERF_INVALID_PARAMETERS` с именем параметра и типом.
- **Ресурсы СКД** (T-000301): каждый `resources[]` даёт `totalField` схемы с
  серверным выражением `Функция(Поле)` (`КоличествоРазличных` →
  `Количество(Различные Поле)`); свободные клиентские выражения не принимаются.
  Эффект — итоги по ресурсным полям на уровнях группировок и в общем итоге.
- **Группировки** (T-000301): `groups[]` — уровни сверху вниз, каждый уровень
  ≥1 поля (несколько полей на уровне — одна группировка по кортежу); структура
  настроек — вложенные группы, детальные записи внутренним этажом
  (`totalsOnly: true` — детальный этаж не добавляется). Уровней ≤ 5.
  **Запрет пересечения:** поле не может быть одновременно ресурсом и
  группировкой → `ERF_INVALID_GROUPS`.
- **Порядок колонок отчёта = порядок `fields[]`** (селекция настроек его
  повторяет). Рекомендация клиенту: группировочные поля в начале `fields[]`,
  ресурсные — в конце.
- Результат детерминирован: одинаковый вход → байт-в-байт одинаковый файл.
  Кеширование на сервере не применяется — повторный запрос это повторная генерация.

### Приватность

`queryText` не пишется в операционные логи сервера: логируются только request id,
длительность, исход и размер артефакта.

**Диагностический аудит (T-000336, REQ-062, v0.84.0):** каждая попытка генерации
дополнительно фиксируется в отдельном защищённом хранилище с точными входными
байтами тела (включая битый JSON) и исходом. Это не операционный лог: содержимое
доступно только администраторам и удаляется по настраиваемому retention (дефолт
30 дней). Секретные заголовки (`Authorization`, `X-Product-Key`, `X-QC-Token`)
не сохраняются никогда; `X-Request-ID` сохраняется как корреляционный идентификатор.

**Errors** (JSON, стандартный конверт):

- `ERF_INVALID_REQUEST` (400) — битый JSON; пустые `queryText`/`reportName`/`fields`;
  пустое имя поля, дубль поля, управляющие символы; больше 500 полей
- `SESSION_NOT_FOUND` (404, T-000336) — непустой `sessionId` не принадлежит текущим
  `user + product` (или синтаксически невалиден)
- `ERF_INVALID_OBJECT_NAME` (400) — `objectName` не является идентификатором 1С
- `ERF_UNSUPPORTED_PARAMETERS` (400) — `&параметр` запроса без описания в
  `parameters` или одиночный член периодной пары; имена перечислены в `message`
- `ERF_INVALID_PARAMETERS` (400, v0.77.0) — структурное нарушение `parameters`:
  дубликат/пустое имя, описание отсутствующего в запросе параметра, пустой или
  неподдержанный тип (имя и тип — в `message`); больше 100 описаний
- `ERF_INVALID_QUERY` (400, v0.77.0) — запрос структурно несовместим с СКД:
  `АВТОУПОРЯДОЧИВАНИЕ` либо результатный пакет не последний (причина — в `message`)
- `ERF_INVALID_RESOURCES` (400, T-000301) — функция вне enum'а, поле ресурса вне
  `fields[]`, пустое имя, одно поле ресурсом дважды
- `ERF_INVALID_GROUPS` (400, T-000301) — поле группировки вне `fields[]`, пустой
  уровень, повтор поля, пересечение с ресурсами, больше 5 уровней,
  `totalsOnly` без `groups`
- `ERF_BODY_TOO_LARGE` (413) — тело больше 8 МБ или `queryText` больше 4 МБ
- `RATE_LIMIT_EXCEEDED` (429) — превышен лимит генераций
- `ERF_GENERATION_FAILED` (500) — внутренняя ошибка сборки (нарушение инварианта
  шаблона / verify-цикла); артефакт не отдаётся

## POST /v1/api/processors/generate-epf

Генерирует внешнюю обработку 1С (`.epf`, БСП «ДополнительнаяОбработка») из BSL-кода
и возвращает готовый бинарь в теле ответа (F-000035, v0.81.0). Канонический шаблон
обработки — у сервера; клиент передаёт только код и имена.

Auth и rate-limit — как у `generate-erf`: `Authorization: Bearer` + `X-Product-Key`,
**30 запросов / 5 минут** на пользователя (свой bucket, с generate-erf не общий).

**Request:**
```json
{
  "code": "string, required — BSL-код: ТОЛЬКО тело процедуры ВыполнитьКодОбработки(), без заголовка и КонецПроцедуры; ≤ 1 МБ",
  "objectName": "string, required — техническое имя обработки: идентификатор 1С (буквы/цифры/подчёркивания, не с цифры)",
  "displayName": "string, required — отображаемое имя (синоним объекта, наименование БСП-регистрации)",
  "version": "string, optional — версия обработки (ВерсияОбработки()); отсутствует/пустая → \"1.0\"; ≤ 64 байт",
  "sessionId": "uuid, optional — привязка попытки к диалогу в аудите генераций; семантика 1:1 с generate-erf (T-000336)"
}
```

**Response (200)** — бинарь, не JSON; заголовки идентичны `generate-erf`
(`Content-Disposition` с `<objectName>.epf`, `Content-Length`, `X-Checksum-Sha256`).
Частичный EPF невозможен: тело пишется после полной сборки и verify-цикла.

### Правила генерации

- `code` вставляется внутрь процедуры `ВыполнитьКодОбработки()` шаблонного модуля
  (каждая строка получает отступ процедуры; переводы строк нормализуются).
  **Границы процедур/функций в `code` запрещены**: `Процедура`/`Функция`/
  `КонецПроцедуры`/`КонецФункции` (и англ. эквиваленты) вне строковых литералов и
  комментариев → 400 `EPF_INVALID_CODE`. Вспомогательные подпрограммы кода —
  оформлять внутри тела нельзя; при потребности в них шаблон расширяется через
  сервер (новый REQ).
- `objectName` → техимя объекта (дескриптор + `ИмяЭтойОбработки()`),
  `displayName` → синоним + `СинонимЭтойОбработки()` (наименование в регистрации
  БСП), `version` → `ВерсияОбработки()`. Кавычки в `displayName`/`version`
  эскейпятся автоматически.
- Обработка регистрируется БСП как «ДополнительнаяОбработка» с двумя командами
  (открытие формы + серверный вызов) — механика шаблона, клиент на неё не влияет.
- Результат детерминирован: одинаковый вход → байт-в-байт одинаковый файл.
  Кеширования нет — повторный запрос = повторная генерация.

### Приватность

`code` не пишется в операционные логи сервера — только request id, длительность,
исход и размер артефакта (политика `generate-erf`). Диагностический аудит
(T-000336) действует и здесь — см. раздел «Приватность» `generate-erf`.

**Errors** (JSON, стандартный конверт):

- `EPF_INVALID_REQUEST` (400) — битый JSON; пустой `code`/`displayName`;
  управляющие символы в `displayName`; `version` длиннее 64 байт
- `SESSION_NOT_FOUND` (404, T-000336) — непустой `sessionId` не принадлежит текущим
  `user + product` (или синтаксически невалиден)
- `EPF_INVALID_OBJECT_NAME` (400) — `objectName` не является идентификатором 1С
- `EPF_INVALID_CODE` (400) — `code` содержит границы процедур/функций (найденное
  слово — в `message`)
- `EPF_BODY_TOO_LARGE` (413) — тело больше 2 МБ или `code` больше 1 МБ
- `RATE_LIMIT_EXCEEDED` (429) — превышен лимит генераций
- `EPF_GENERATION_FAILED` (500) — внутренняя ошибка сборки; артефакт не отдаётся
